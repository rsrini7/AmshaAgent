### LS-1 — Typed UI/Backend Contract DTOs
**Verdict: ✅ Valid, but defer.** The UI appears minimal/experimental based on the overall architecture. The OpenAPI generator adds a Maven build step, a codegen lifecycle, and a TS npm pipeline coupling. The payoff is low until the UI surface stabilizes. Revisit when the REST API surface freezes. 

### LS-2 — `ToolExecutionContext` Parameter
**Verdict: ✅ High value — but sequence carefully.** The logs confirm `WorkspaceContext` static accessors are called from 10+ tool invocations per session.  This is the single biggest architectural smell — tools are implicitly stateful. However, this is a **30+ tool migration** that touches every tool's `execute()` signature. Doing it *before* LS-3 means you'd migrate 30 tools twice if LS-3 changes `ToolResponse`. **Correct sequence: LS-3 → LS-2.** Also note: the new `StepDecisionRouter` and `SequentialToolExecutor` extracted in this refactor are clean insertion points for `ToolExecutionContext` — the groundwork is already laid. 

### LS-3 — Sealed `ToolResponse` Hierarchy
**Verdict: ✅ Do this first among the LS items.** The `ToolResponse` flat record with `boolean success` and `isInfraFailure()` is already accumulating flags — you can see it in the diff where `response.isInfraFailure` is checked separately from `response.success`.  A sealed hierarchy (`ToolSuccess`, `ToolFailure`, `ToolPending`) eliminates these flag checks at compile time. **This is the highest ROI item on the list and unblocks LS-2.** 

### LS-4 — Sealed `ReasoningStep` Hierarchy
**Verdict: ✅ Valid, medium priority.** The `StepDecisionRouter` introduced in this refactor is exactly where `instanceof` pattern matching on a sealed `ReasoningStep` would shine — the `if ReasoningStep.FINISH.equals(step.action)` string dispatch is the clearest pain point.  This is **safe to parallelize with LS-2** once LS-3 is done. 

### LS-5 — Split `MessageContext` into Domain + Transport
**Verdict: ⚠️ Valid but risky sequencing.** `MessageContext` flows through the entire pipeline. The `ResumeStrategyDispatcher` was just extracted and takes `MessageContext` directly.  Splitting it now would be a wide blast radius across handlers, reflexes, and resume paths. **Defer to after LS-2/LS-4 stabilize.** Consider making it a composition (`MessageContext` holds a `TransportContext` field) rather than a full split, which is less disruptive. 

### LS-6 — Tool SPI Lifecycle Hooks
**Verdict: ✅ Low risk, standalone.** Default interface methods on `AgentTool` — zero migration cost for existing tools. The logs show Playwright and the Podman sandbox already do informal health-checking (`SandboxValidator`, `ProcessIsolationExecutor` warn).  This formalizes what already exists. Can be done in isolation at any time. 

### LS-7 — HITL Typed `ApprovalFrame`
**Verdict: ✅ Good, do alongside UI work.** The approval messages currently look like `"⏸ Approval needed for tool: github... 📋 Params: {\"action\":\"repo\"...}"` — pure string construction.  A typed `ApprovalFrame` record would make the UI rendering deterministic and enable risk-level badging. Pair this with LS-1 when the UI matures. 

### LS-8 — Postgres WORM Audit Triggers
**Verdict: ✅ Required for production, but not yet urgent.** The current SQLite adapter is confirmed working correctly — checkpoints cycle cleanly and the `ComplianceAuditService` fires `AUDIT-MANDATORY` events.  This is a production-hardening item for when the system moves beyond single-instance SQLite. Creating the `arcclaw-persistence-postgres` module is the right call, but only once the port interface stabilizes (post LS-2/LS-3).

## Additions to Lock In Before Exit

### Phase 1 — LS-3 Sealed `ToolResponse`

One design detail to specify explicitly: the `ToolPending` variant is for async/HITL-suspended tool calls, not just slow tools. Make sure the record carries a `checkpointId` or `approvalToken` field so the HITL resume path in `ResumeStrategyDispatcher` can reconstruct context without hitting the store again. Otherwise `ToolPending` becomes a hollow placeholder and the state machine still falls back to `isInfraFailure`-style flag checking just with different names.

### Phase 2 — LS-2 `ToolExecutionContext`

The plan says "migrate all 30+ tools" but doesn't address the `WorkspaceContext` static accessor itself. After migration, `WorkspaceContext.run(...)` and `WorkspaceContext.requireUserId()` must be deprecated and their call sites deleted — not just bypassed. Otherwise the implicit statefulness stays in the codebase and new tools will keep using the static path. Add an explicit cleanup step: **zero remaining callsites to `WorkspaceContext` static accessors** as the exit criterion for LS-2.

### Phase 2 — LS-4 Sealed `ReasoningStep`

The plan says `StepDecisionRouter` gets `switch` pattern matching, but `EngineStepHandler`, `FinishActionHandler`, and `ReasoningStepParser` all do their own string-dispatch on `step.action`. Those three must be included in the LS-4 blast radius or the sealed hierarchy won't actually eliminate the string constants — they'll just move them. Pin this explicitly in the scope.

### Phase 3 — LS-7 `ApprovalFrame`

The `riskLevel` field in `ApprovalFrame(tool, params, riskLevel)` needs a concrete enum or type defined now, not during implementation. The Telegram approval message already shows the tool name and params in plain text — the only new value `ApprovalFrame` adds over the current string is structured risk classification. Without committing to the enum (`LOW / MEDIUM / HIGH / CRITICAL` or similar) in the plan, the backend and UI will implement it differently and you'll have a contract drift problem that LS-1 was supposed to solve.

### Phase 4 — LS-8 Postgres

The plan says "fresh Flyway scripts" but the existing SQLite schema uses SQLite-specific types and pragmas. The Flyway baseline for Postgres needs explicit mention of the schema translation step — particularly `BOOLEAN` vs `INTEGER` for status flags, and the `TEXT` JSON columns that will become `JSONB`. This is not just a copy-paste migration.
