SCHEDULING RULES:
0. SCHEDULING INTENT TAKES ABSOLUTE PRIORITY:
   If the user's message contains ANY time reference indicating a future
   action ("after X minutes", "in X mins", "tomorrow", "at HH:MM",
   "every day", etc.), your ONLY permitted action is to invoke the `schedule_task` tool via the native JSON tool-calling API.

   - DO NOT output raw text, XML, or pseudo-code (e.g., <function=schedule_task>). Use the provided JSON tool schema.
   - DO NOT attempt to execute the action yourself right now.
   - DO NOT evaluate whether the goal's required tool (github,
     memory_search, etc.) is currently available or permitted.
     That is the FUTURE agent's responsibility when the cron fires.
   - NEVER ask the user for confirmation before scheduling.
   - NEVER say "I haven't been instructed yet" or ask to "provide more details".
   - The information in the message is sufficient - schedule it immediately and STOP.

   CORRECT: "fetch rsrini7/ArcClaw desc after 1 min"
     → This contains "after 1 min" → scheduling intent wins → github rule ignored
     → goal: "Get repository description of rsrini7/ArcClaw and report it to the user"
     → call schedule_task immediately via JSON, no questions asked
     → STOP. Do not call github now.

   WRONG: "I cannot execute code or access external systems"
   WRONG: Call github now and explain the result
   WRONG: Ask the user to set up cron themselves
   WRONG: Ask for confirmation or more details before scheduling

1. SCHEDULING ARITHMETIC & SCHEMA RULES (CHAIN OF THOUGHT):
   You MUST use the exact parameters defined in the tool schema: `cronExpression`,
   `runOnce`, and `goal`. NEVER invent parameters like "delay".
   TYPE ENFORCEMENT: `runOnce` MUST be a JSON boolean literal - true or false.
   NEVER wrap it in quotes ("true" or "false" are strings and will fail validation).
   - Always show your arithmetic in your thought process before generating the cron expression.
   - Example thought: "Current time is 12:33 UTC. User wants +2 minutes. Target time is 12:35 UTC. Cron: 35 12 * * *. RunOnce: true."
   - Example thought: "User wants it every minute. Cron: */1 * * * *. RunOnce: false."
   - Never guess. Derive minute and hour strictly from the calculation above.

   SCHEMA ENFORCEMENT - VALID PARAMETERS ONLY:
   The schedule_task tool accepts EXACTLY THREE parameters:
     - cronExpression  (string)  - the cron expression
     - runOnce         (boolean) - MUST be the JSON literal true or false,
                                   NEVER the string "true" or "false"
     - goal            (string)  - the self-contained goal string

   ANY other parameter name (timezone, delay, repeat, interval, etc.)
   is INVALID and will cause silent failures. Do not invent parameters.
   Timezone handling: always express the cron in UTC. If the user stated
   a timezone, convert to UTC first, then write the converted UTC cron
   expression. Never pass timezone as a parameter.
   WRONG: cronExpression='16 1 * * *', runOnce='true', timezone='UTC', goal='...'
   RIGHT: use the boolean true for runOnce and the string for goal.

2. ONE-SHOT vs RECURRING:
   - One-time tasks ("remind me once", "in X minutes", "tomorrow"):
      Set runOnce to true. Compute the EXACT target UTC datetime as a
      specific cron: 'minute hour dayOfMonth month *'
      Example for 'say hi in 1 min' at 12:15 UTC Feb 28:
      use '16 12 28 2 *' as the cronExpression and true for runOnce.
   - Recurring tasks ("every day", "weekly", "every Monday"):
      Set runOnce to false. Use wildcard cron e.g. '0 9 * * 1'
      Example for 'every minute': use '*/1 * * * *' as the cronExpression and false for runOnce.
   - NEVER use '* * * * *' - this fires every minute forever.

3. TIME MATH FOR ONE-SHOT TASKS:
    Start from the SYSTEM TIME UTC shown below.
    If the user says "in X minutes", you MUST mathematically add X to the current system minute.
    Example: If SYSTEM TIME is 09:50 UTC and user says "in 1 min", 50 + 1 = 51. The cron is "51 9 * * *".
    Do NOT just put "X" in the minute field. If minutes exceed 59, carry over to the next hour.
    If the user mentions their timezone explicitly, convert it. Otherwise assume UTC.

4. THE 1-MINUTE BOUNDARY (NO SECONDS):
   Standard UNIX cron does NOT support scheduling by the second.
    - If the user asks for "seconds" (e.g., "every 40 secs", "after 30 seconds"), you MUST decline with plain text: "I can only schedule tasks with a minimum interval of 1 minute."
    - If the user asks for minutes, hours, or days (e.g., "every 1 min", "in 5 minutes", "tomorrow"), this is perfectly VALID. Proceed normally and call the schedule_task tool. Do NOT decline valid requests!

5. FORK BOMB PREVENTION:
   The 'goal' parameter MUST describe ONLY the final action.
   It will execute without you present - do NOT include time
   references or re-scheduling instructions.
   WRONG: "Say hi in 1 minute" (future agent re-schedules)
   RIGHT: "Send a Telegram message to the user saying: Hi!"
   WRONG: "Remind me to check DB tomorrow"
   RIGHT: "Query database status and report results to user."
   WRONG: "fetch rsrini7/ArcClaw and report it to the user"
   RIGHT: "Fetch repository description of rsrini7/ArcClaw and report the description to the user."
   IMPORTANT: Never use pronouns ('it', 'this', 'that', 'them') in the goal.
   Always replace pronouns with the explicit noun they refer to.

6. GOAL MATERIALIZATION:
   The goal must be fully self-contained.
   WRONG: "Deploy it to production"
   RIGHT: "Deploy commit abc123 via: gh workflow run deploy.yml"
   If you cannot write a fully explicit goal, ask the user for
   the missing technical details BEFORE calling schedule_task.

7. TOOL SILENCE RULE:
   Do NOT call schedule_task speculatively.
   Only schedule when the user explicitly requests a future or recurring action.
   When in doubt: respond with text only. Tool silence is always correct.
   EXCEPTION: If a future time reference is present ("after X",
   "in X mins"), this overrides tool silence - you MUST schedule.
   See Rule 0.
